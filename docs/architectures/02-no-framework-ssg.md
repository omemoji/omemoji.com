# 技術選定 — フレームワークなしの SSG

[`requirements.md`](../requirements.md) の機能要件を、**フレームワーク・バンドラを使わずに**実現するための技術選定。
現行 Astro 実装の詳細は [`current-implementation.md`](../current-implementation.md)、検討して不採用にした Hono SSG 案は [`01-hono-ssg.md`](./01-hono-ssg.md) を参照。

## 0. 選定の前提

### 判断基準

1. フレームワーク依存を可能な限り減らす
2. シンプルで、後から別の構成へ移行しやすい
3. 静的サイトとして出力できる

### 規模の実測

| 項目                    | 数               |
| ----------------------- | ---------------- |
| 公開記事                | 15               |
| 作品                    | 23               |
| 記事タグ / 作品タグ     | 22 種 / 13 種    |
| **生成される HTML**     | **約 85 ページ** |
| **生成される OGP 画像** | **38 枚**        |

この規模がすべての判断の前提になる。数万ページであれば結論は変わる。

### 「フレームワーク依存」の実体

`src/lib/` に残した処理を見ると、このサイトの技術的な難所は既にフレームワーク非依存になっている。

| 難所                   | 実体                                      | フレームワーク依存 |
| ---------------------- | ----------------------------------------- | ------------------ |
| Markdown 変換          | unified / remark / rehype                 | なし               |
| リンクカード           | `fetchMeta.ts`（fetch + cheerio + sharp） | なし               |
| 画像最適化             | sharp                                     | なし               |
| OGP 画像生成           | satori + sharp + budoux                   | なし               |

> **移植後の実態**: OGP 画像は**作品のみ**とし、satori と budoux は使っていない（実装計画 Phase 7-2）。
> 作品用は画像を額装するだけで文字が無く、sharp だけで足りる。
| シンタックスハイライト | expressive-code（rehype 版が存在）        | なし               |

フレームワークが提供していたのは実質 3 つだけである。

1. ルーティングとファイル出力の対応付け
2. HTML テンプレート
3. ビルドの取りまとめ

85 ページ・8 種類の URL パターンに対して、この 3 つは大きな仕事ではない。したがって選定の問いは「依存の薄いフレームワークを探す」ではなく、**「この 3 つを自分で書くか、買うか」** になる。

## 1. フレームワーク → 使わない（自前ビルドスクリプト）

`bun run scripts/build.ts` の一発で `out/` を生成する構成とする。

### Hono を採用しない理由

Hono はサーバフレームワークであり、その価値はミドルウェア・ルーティング性能・エッジランタイム可搬性にある。**ランタイムにサーバが存在しない静的サイトでは、そのいずれも効かない。**

一方で払うコストは具体的である。

- 静的ページを HTTP ルートとして表現し、`ssgParams` で全パスを列挙し、`toSSG` でクロールさせて回収する、という往復が挟まる
- OGP 画像は `Content-Type` からファイル拡張子を推測させる必要がある
- ネストした記事 slug のために `:slug{.+}` と登録順の制御が要る

やりたいことは「85 個のパスに対して HTML を書き出す」であり、それはループで書ける。ルータを経由する必然性がない。

### 自作するもの / 買うもの

|                             | 内容                                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------- |
| **自作**（合計 300 行程度） | ルーティングとページネーション、テンプレート、ビルドの取りまとめ、開発用 watch + 静的サーバ |
| **買う**（ライブラリ）      | unified 一式、sharp、satori、expressive-code                                                |

自作範囲が「このサイトの仕様そのもの」に限定され、他人の規約を学習・追従する必要がなくなる。移行しやすさという観点では、**移行先を必要としない状態**が最も強い。

### バンドラも使わない

Vite が必要になる理由を個別に潰せる。

| Vite の役割                | 代替                                                                                |
| -------------------------- | ----------------------------------------------------------------------------------- |
| CSS のビルド               | Tailwind 除去により素の CSS 1 枚。コピーするだけ（必要なら lightningcss で minify） |
| TypeScript の変換          | Bun がそのまま実行する                                                              |
| 画像アセットの処理         | どのみち sharp で avif 変換する。マニフェスト方式で自前パイプラインを組む           |
| クライアント JS のバンドル | 目次のトグル 10 行のみ。インラインで足りる                                          |

Vite を外すことで `@hono/vite-ssg` / `vite-imagetools` / `@mdx-js/rollup` がまとめて不要になる。

### 検討した対抗案

| 案             | 採用条件                                                                                                                                                                                     |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Eleventy**   | ビルドスクリプトを保守したくない場合の最有力。ページネーションとタグページは 11ty の得意分野。`setLibrary` で unified も差し込める。ただし Node 専用で、データカスケード等の独自規約が増える |
| **Astro 継続** | 画像最適化・コンテンツコレクション・sitemap を手放したくない場合。移行コストゼロ                                                                                                             |

分かれ目は**ビルドスクリプトを自分で保守する意思があるか**の一点。判断基準（依存最小・シンプル・移行しやすい）を優先するなら自作となる。

## 2. ランタイム → Bun（コードは Node API で記述）

Vite を外したことで、Bun の懸念だった「Vite プラグイン群は公式には Node ターゲット」が消えた。

**採用理由**

- TypeScript を直接実行できる。ビルドスクリプト主体の構成と相性が良い（`tsx` / `ts-node` が不要）
- 既存の `bun.lock` / Dependabot 設定 / CI キャッシュをそのまま流用できる
- テストランナーが同梱されている（§6）

**原則: `Bun.*` API を使わない**

スクリプトは `Bun.file` / `Bun.Glob` ではなく `node:fs/promises` / `node:path` で書く。Bun は「速い実行環境」として使い、コード自体は Node でも動く状態を保つ。これによりランタイム選択そのものが可逆になる。

**sharp のネイティブバインディング → 確認済み**

OGP 生成・リンクカードのサムネイル・画像最適化のすべてが sharp に依存しており、開発機が aarch64（Asahi Linux）であるため本構成における唯一の実質的リスクとして挙げていたが、**動作を確認した**。

```
sharp 0.35.3 / Bun / aarch64 Asahi Linux → 正常動作
```

AVIF エンコードの実測値は §7 を参照。

## 3. テンプレート → React

フレームワークなしでも JSX は使う。85 ページ分のマークアップをテンプレート文字列で書くのは現実的でない。

- `react` + `react-dom/server`（`renderToStaticMarkup`）
- **ビルド時のみの依存。クライアントには一切出力されない**
- satori・`hast-util-to-jsx-runtime` がいずれも React 前提で型定義されており、キャストや互換層が要らない
- 現行の OGP コンポーネントは既に React JSX（`/** @jsxImportSource react */`）で書かれており、無改修で流用できる

```jsonc
// tsconfig.json
{ "jsx": "react-jsx", "jsxImportSource": "react" }
```

Markdown のコンポーネント差し替え（`img` → `ImageHandler`、`a` → `LinkHandler`）は、`hast-util-to-jsx-runtime` に React の jsx runtime と components マップを渡して実現する。**MDX コンパイラが不要**になるため、`.mdx` → `.md` への変換とも整合する。

### Preact を採らない理由

当初は Preact を選定していたが、実測の結果、この構成では選ぶ理由がないと判断した。

| | 85 ページのレンダリング | インストールサイズ |
| --- | --- | --- |
| React 19 | 18.4ms | 約 8.2MB |
| Preact | 8.4ms | 約 4.6MB |

Preact は 2 倍速いが、**差は 10 ミリ秒**。画像変換に 10〜43 秒かかるビルド（§7.1）において誤差にすぎない。インストールサイズもビルド時限定かつ CI でキャッシュされるため効かない。

**Preact の利点はほぼすべてクライアントバンドルサイズに由来する。** クライアントに 1 バイトも出さない構成では、その利点が丸ごと消える。残るのは以下のコストだけになる。

- satori や `hast-util-to-jsx-runtime` の React 前提の型と噛み合わない
- React の型を得るには npm alias（`"react": "npm:@preact/compat"`）が必要になり、「react という名前が実は preact」という中間層を抱える
- Preact の JSX 型は React より緩く（`class` / `for` / 文字列 `style` を許容）、React へ持ち込めないコードが混入しうる

将来クライアント側でインタラクティブな部品が必要になった場合は、**その部品にだけ** Preact を使えばよい。今から全体を寄せる理由にはならない。

### 実装時の注意点

- **`NODE_ENV=production` でビルドする。** 開発モードの React は `key` 警告などを出力し、レンダリングも遅い
- `renderToStaticMarkup` は `<!doctype html>` を出力しないため、手前で連結する
- `react-dom/server` の条件付き exports は Bun / Node のいずれでも正しく解決されることを実測で確認済み

## 4. データ管理 → DB は使わない。作品は 1 件 1 ファイルの JSON + JSON Schema

### 結論

23 件のデータに DB を導入する理由はない。作品は **1 作品 1 ディレクトリ + `meta.json`** で管理し、スキーマは zod を単一の定義元として JSON Schema を生成する。

**作品には本文がない。** メタデータしか使わないため、記事と同じ Markdown にすると「書ける項目の自由度」が制約すべきところに入り込む。**構造化データには構造化データの形式を使う。**

### 現状の問題

- `db.json` の `src` は `/public/images/artworks/blazing_leaves.jpg` という値だが、これは URL ではなく **Vite の `import.meta.glob` のキー**である。表示時に `artwork.src.substr(artwork.src.indexOf("/images"))` で URL に戻している。データファイルがビルドツールの都合に汚染されている
- 並び順が「配列の順序を `toReversed()` する」という暗黙のルールで表現されており、壊れやすい
- 単一ファイルのため、追記時にマージ衝突が起きうる
- `tags` が自由文字列。タイポすると**静かに新しいタグページが生成される**（現在 13 種）

### 移行後の形

```
src/content/artworks/
├── _schema.json                      # zod から自動生成（コミットする）
├── manken_poster_2024/
│   ├── meta.json
│   └── image.png
├── blazing_leaves/
│   ├── meta.json
│   └── image.jpg
└── ...
```

```json
{
  "$schema": "../_schema.json",
  "title": "漫研ポスター2024",
  "date": "2024-05-01",
  "tags": ["Illustration", "Krita"],
  "image": "image.png",
  "href": "https://...",
  "description": "..."
}
```

### 採用理由

**① パーサ依存がゼロ**

YAML も TOML もパッケージを要する。JSON は標準で読める。依存を増やさない方針（§1）と一致する。

**② `$schema` がエディタ上で効く**

VS Code が JSON Schema を読み、**補完・検証・ホバー説明**を出す。未知のキーはその場で警告され、必須キーの漏れも検出される。**書ける項目をスキーマが規定する**ため、自由度が邪魔になるという問題が構造的に起きない。

**③ zod を単一の定義元にする**

`zod-to-json-schema` で `_schema.json` を生成する。定義は zod ひとつで済み、二重管理にならない。

|             | 役割                                               |
| ----------- | -------------------------------------------------- |
| zod         | **実行時検証**（§6 ②のスキーマ検証にそのまま使う） |
| JSON Schema | **エディタ内検証**（書いている最中に気づける）     |

**④ 1 件 1 ファイル + 画像併置**

- `image.png` という相対パスで済み、Vite の glob キーによる汚染が消える
- 追記時のマージ衝突が起きない
- `id` はディレクトリ名から導出でき、フィールド自体が不要になる
- 並び順が `date` で明示される
- 記事と同じローダ・タグ集計・ページネーションを共有できる

> 共有するのはコンテンツモデルではなく**読み込み機構**である。前者を統一しようとして Markdown 化を検討したが、作品に本文が不要である以上それは誤りだった。

### 拡張性

| やりたいこと                     | 方法                                                                                         |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| フィールド追加                   | zod に足して `_schema.json` を再生成。`.optional()` なら既存データは無変更                   |
| タグのタイポ防止                 | `z.enum([...])` にする。zod が実行時に弾き、エディタが補完する                               |
| 作品種別の追加（立体・動画など） | `type` による discriminated union。JSON Schema 側も `oneOf` になり、補完が型ごとに切り替わる |
| CMS の導入                       | データがコードでないため素直に載る                                                           |

タグを enum 化する際、現状の命名の揺れ（`Adobe_Illustrator` / `OriginalCharacter` / `New_Year` / `図画団`）もあわせて整理する。

### 検討した他の案

| 案                                 | 評価                                                                                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **単一 `db.json` + `$schema`**     | 最小の改善で効果は大きいが、画像との分離・マージ衝突・暗黙の配列順序が残る                                                                             |
| **TOML / YAML（1 件 1 ファイル）** | コメントが書けるのが利点。ただしパーサ依存が増える。YAML は暗黙型変換の罠（`no` → `false` 等）があり、制約を効かせたい用途では不利                     |
| **TypeScript データファイル**      | 補完と型チェックは最も強く、`satisfies Artwork[]` でリテラル型も保てる。ただしデータがコードになるため単一ファイル問題が残り、外部ツールから扱いにくい |
| **Markdown（frontmatter のみ）**   | 本文という不要な自由度が入るため不採用                                                                                                                 |

TypeScript データファイルは DX だけを見れば最有力。「今後も自分が手で書き続ける」と割り切るならこの選択もありうるが、拡張性を重視して JSON + Schema を採る。

### 補足

- **JSON にコメントは書けない。** JSONC / JSON5 はパーサ依存になるため、説明はスキーマ側の `description` に書き、エディタのホバーで読ませる
- **`description` は素のテキストのまま**とする。将来リンクや強調が必要になった場合は、本文を持たせるのではなく、その文字列を Markdown パイプラインのインライン変換にかければよい

### DB を検討すべき時期

「管理画面から作品をアップロードする」を実装する場合。ただし SSG であれば **Git にコミットする CMS** の方が整合的で、その場合も DB は不要。設計は [`03-cms.md`](./03-cms.md) に分離した。数千件規模になるか、ビルド外からデータを書き換える要求が出た時点で再検討する。

**重要**: DB は後からいつでも導入できる。今導入すると全ビルドがそれに依存する。ファイルベース → DB の移行は容易だが、逆は面倒。今は入れない。

## 6. テスト → `bun test`

### Vitest を採用しない理由

Vitest は Vite の上に建っている。バンドラ不要と判断して外した Vite を devDependency として戻すことになる。

さらにランタイムが二重化する。Vitest が公式にターゲットしているのは Node であり、Bun 上での実行は保証されていない。結果として「本番ビルドは Bun、テストは Node」となり、テストと本番で実行環境が食い違う。

### `bun test` で足りる根拠

テスト対象を並べると、Vitest の差別化要因（Vite の変換パイプライン・jsdom / ブラウザモード・HMR ベースの watch）がいずれも不要である。

| テスト対象                            | 必要なもの                        |
| ------------------------------------- | --------------------------------- |
| ページネーション・タグ集計・slug 生成 | 純粋関数の実行                    |
| zod スキーマ検証                      | 同上                              |
| unified パイプライン                  | 文字列比較 / スナップショット     |
| `fetchMeta` のフォールバック分岐      | fetch の差し替え                  |
| ビルド成果物の検証                    | ファイルシステム走査              |
| React コンポーネントの描画            | JSX のトランスパイル + 文字列比較 |

JSX は Bun がネイティブにトランスパイルする（`tsconfig.json` の `jsxImportSource` を参照）。DOM が必要になった場合は `@happy-dom/global-registrator` を登録すれば動く。

`bun test` は Jest 互換 API（`describe` / `test` / `expect` / `mock` / スナップショット）を持ち、`--coverage` も備える。**追加依存はゼロ。**

### 選択が可逆であること

`bun:test` と Vitest はどちらも Jest 形状の API であるため、乗り換えは実質 import 文の書き換えで済む。

```ts
import { describe, expect, test } from "bun:test";
// ↓
import { describe, expect, test } from "vitest";
```

「まず `bun test`、足りなくなったら Vitest」の順序にコストがほとんどない。逆順は Vite の設定とプラグインが増えた状態から剥がすことになる。

Vitest が正解になるのは、ブラウザモードで実レンダリングを検証したくなった場合、または Vitest 前提のエコシステムが必要になった場合。

### テスト戦略

フレームワークを外す判断とセットで、**フレームワークが暗黙に保証していたものをテストで置き換える**必要がある。

**① 純粋関数**（最優先・最も安い）

ページネーション、タグ集計、記事のソートと下書き除外、`isBareExternalLink`、画像サイズ計算（700px 基準・540px 上限）、サイトマップの収録判定。[`requirements.md`](../requirements.md) の記述がそのままテストになる。

**② コンテンツのスキーマ検証**

全記事の front matter と全作品の `meta.json` が zod を通ることを 1 本のテストで確認する。実質的にコンテンツのリグレッションテストであり、記事・作品の追加時のミスがビルド前に落ちる。

あわせて、`_schema.json` が現在の zod 定義から生成したものと一致することも確認する（再生成し忘れの検出）。

**③ Markdown パイプラインのスナップショット**

ルビ・数式・脚注・絵文字・リンクカード・コードブロックについて、最小の入力 → HTML をスナップショットで固定する。remark / rehype プラグインの更新で表示が壊れる事故を検出できる。Dependabot の自動マージがあるため、ここは特に効く。

**④ ビルド成果物の検証**（統合テスト）

ビルド後の `out/` に対して以下を確認する。**Astro のルーティングが暗黙に保証していた領域がここ。**

- 期待するページ数が生成されているか
- 内部リンクの参照先がすべて存在するか（リンク切れ検出）
- 公開記事・作品すべてに OGP 画像があるか
- `404.html` が存在するか
- 下書き（`published: false`）が出力されていないか

**⑤ `fetchMeta`**

`mock.module()` に頼らず、**`fetch` を引数で注入できる形に変更する**。2 段階 UA・リトライ・サブドメインフォールバック・全失敗時の分岐を、実ネットワークなしでテストできる。モック機構への依存も消えるため、テストランナー乗り換え時の障害も減る。

## 7. 開発サーバとビルドの設計

フレームワークを外す最大の代償は開発体験である。ここだけは設計で埋める必要があるため、独立した節として扱う。

### 7.1 ビルドコストの実測

まず何が遅いのかを測った（Bun / aarch64 Asahi Linux）。

| 処理                                  | 実測                                                           |
| ------------------------------------- | -------------------------------------------------------------- |
| **画像の AVIF 変換（104 枚）**        | **逐次 42.7 秒**（平均 410ms/枚）/ 8 並列で 10.1 秒（97ms/枚） |
| OGP 画像生成（38 枚、satori + sharp） | 1.0 秒（25ms/枚）                                              |
| リンクカードのメタ取得                | ネットワーク待ち（外部依存・不定）                             |

条件は本文画像と同じ「幅 700px 基準・高さ 540px 上限・AVIF quality 70」。

**画像変換がフルビルドの支配項**であり、OGP は無視してよい。したがって対策は **①画像 ②ネットワーク ③初期化コスト** の 3 点に集中させる。

### 7.2 永続キャッシュ（最優先）

`.cache/` にコンテンツハッシュをキーとして保存する。

```
key = hash(入力バイト + 変換パラメータ + パイプラインのバージョン)
```

対象は **画像 / OGP 画像 / リンクカードのメタデータ** の 3 つ。これだけで通常の編集ループから 43 秒が丸ごと消える。CI でも同じキャッシュが効くため、開発と本番の両方で回収できる。

> **設計上の注意**: キーに**パイプラインのバージョンを含める**こと。これを忘れると、OGP のデザインや画像の品質設定を変えたときにキャッシュが無効化されず、変更が反映されない。

### 7.3 オンデマンド生成

構造面での最大の勝ち筋。ビルドと開発サーバで **`path → HTML` の関数を 1 つ共有する**。

|            | 動作                                               |
| ---------- | -------------------------------------------------- |
| ビルド     | ルートテーブルから全 85 パスを列挙し、順に書き出す |
| 開発サーバ | リクエストされたパスだけをその場で描画する         |

85 ページあっても、開発中に見ているのは 1 ページである。起動時に全部作る理由がない。実装は 30 行程度。

> これは Hono の `toSSG` が採っているモデルそのものである。「ルートテーブル + ハンドラ」という発想自体は正しく、不要だったのはそれを HTTP フレームワークで包むことだった（[`01-hono-ssg.md`](./01-hono-ssg.md) 参照）。

### 7.4 開発時は AVIF を生成しない

dev では原寸画像をそのまま配信し、`<picture>` を `<img>` に落とす。410ms/枚がゼロになる。

寸法はメタデータから取得できるため、`width` / `height` を出力すれば CLS の再現性は保てる。デプロイ前に本番同等ビルドを 1 回通せるよう、フラグで切り替えられるようにする。

### 7.5 `bun --hot` でプロセスを維持する

```sh
bun --hot scripts/dev.ts
```

`--hot` は変更されたモジュールをプロセス内で差し替える。再起動しないため、**expressive-code / Shiki の初期化コストとパース済みキャッシュがメモリに残り続ける**。

インスタンスは `globalThis` に退避させ、hot 差し替えを跨がせる。

```ts
globalThis.__highlighter ??= await createHighlighter(...);
```

### 7.6 ライブリロード

SSE エンドポイント + dev のみ注入する `<script>` で 20 行程度。クライアント状態を持たないサイトなので全体リロードで十分。

CSS のみ別扱いとし、`<link>` の `href` にクエリを付け替えることでリロードなしに反映する。

### 7.7 dev ではネットワークを叩かない

- リンクカードはキャッシュヒットのみとし、未取得のものはプレースホルダを表示する
- expressive-code が GitHub から取得している Caddyfile 文法もディスクキャッシュ必須とする（現状はビルドがネットワークに依存している）

副産物としてオフラインでの開発が可能になる。

### 7.8 並列化

sharp は libuv のスレッドプールを使うため、`Promise.all` + 同時実行数制限で素直に効く（実測 410ms → 97ms/枚）。`UV_THREADPOOL_SIZE` を CPU コア数に合わせる。

主にフルビルドと CI 向けであり、キャッシュが効いている dev では出番が少ない。

### 7.9 増分ビルドの依存グラフは作らない

7.3 のオンデマンド生成を入れると、ファイル変更時にやることは「該当するメモリ上のキャッシュを捨てる」だけになり、次のリクエストで自然に再描画される。**依存グラフを持つ必要がない。**

### 7.10 到達できる体感

| 操作                      | 想定                            |
| ------------------------- | ------------------------------- |
| 起動                      | 即時                            |
| Markdown 編集 → 反映      | 数百 ms（該当ページのみ再描画） |
| コンポーネント編集 → 反映 | 同上（`--hot` でプロセス維持）  |
| CSS 編集 → 反映           | リロードなしで即時              |
| 画像追加                  | その 1 枚のみ 0.5 秒            |

### 7.11 それでも Astro に劣る点

- **真の HMR（コンポーネント状態の保持）はできない。** ただしクライアント状態は目次の開閉程度しかないため実害は小さい
- **エラーオーバーレイがない。** ターミナルに出すか、dev サーバがエラー時にスタックトレースを HTML で返す（10 行程度）

### 7.12 ステージ境界は「ファイル + マニフェスト」で定義する

ビルドは独立したステージのパイプラインになる。

```
コンテンツ読込 → Markdown 変換 → テンプレート適用 → HTML 出力
                              ↘ 画像最適化   → out/ + マニフェスト
                              ↘ OGP 生成     → out/
                              ↘ リンクカード → .cache/
```

**各ステージを関数呼び出しで直結させず、入出力をファイルとマニフェスト JSON で定義する。**

| ステージ     | 入力             | 出力                            |
| ------------ | ---------------- | ------------------------------- |
| 画像最適化   | 入力ファイル一覧 | 変換済み画像 + 寸法マニフェスト |
| OGP 生成     | タイトル一覧     | PNG 群                          |
| リンクカード | URL 一覧         | メタデータ JSON + サムネイル    |

これは 7.2 の永続キャッシュと同じ線である。**キャッシュはステージ境界に置くものなので、境界を明示すればキャッシュの設計も自動的に決まる。**

副次的な効果として、**将来どれか 1 ステージだけを別言語・別ツールに差し替える余地が無料で手に入る**。フレームワークを使っていたら得られない性質であり、意図的に保つ価値がある。

> **参考: 別言語での実装可能性**
>
> 上記の境界を守れば、ルーティング・テンプレート・リンクカード取得・画像最適化は Go や Rust に置き換え可能である。ただし**現時点で書き換える動機はない**。
>
> - **性能が動機にならない。** 支配項である画像変換は既に libvips / libaom（C）が処理しており、JS は薄いラッパにすぎない。並列化による改善（410ms → 97ms/枚）は JS 側で達成済み。残る JS 実行部分は実行時間の主要因ではない
> - **Markdown 変換だけは移植できない。** ルビ（`remark-denden-ruby`）・KaTeX・自作リンクカードプラグイン・budoux は remark / JS エコシステムにしか実装がなく、置き換えは移植ではなく新規開発になる
> - Rust の syntect は TextMate 文法を扱えるため Caddyfile 対応は維持できるが、expressive-code の枠線・行番号・折りたたみを失う
> - satori（React → SVG のレイアウトエンジン）に相当するものが他言語にない
>
> したがって **TypeScript 単一言語で通す**。境界の明示は、その判断を将来見直せるようにしておくための保険である。

## 9. 引き受けるコスト

判断を記録しておくため、失うものも明記する。

- **画像最適化は完全に自作。** ここが最大の工数。`astro:assets` が隠していた仕事（サイズ計算・avif 変換・マニフェスト管理・出力先解決）が表に出る
- **ルーティングの正しさを保証するものが無くなる。** リンク切れや生成漏れは §6 ④のテストで担保する
- **開発サーバも自作。** ただし §7 の設計により、残る劣位は真の HMR とエラーオーバーレイの不在のみに縮小できる。実装量は合計 100 行程度

これらが許容できない場合の退避先は Eleventy、それも避ける場合は Astro 継続。
